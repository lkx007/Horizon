### [OpenSec discloses CVE-2026-99362: pre-auth heap overflow in Linux kernel nfsd enabling remote root access](https://opensec.in/blog/nfs2root-cve-2026-99362) ⭐️ 9.0/10

OpenSec disclosed CVE-2026-99362, a critical pre-authentication heap overflow vulnerability \(CVSS 9.8\) in the Linux kernel&\#x27;s NFS server \(nfsd\), affecting all versions from 3.16 \(released in 2014\) through recent stable kernels when NFSv4.1 or NFSv4.2 is enabled. The flaw allows unauthenticated remote attackers to execute arbitrary code as root by sending a single crafted packet to TCP port 2049. Fixes are available in kernel versions 6.12.117, 6.18.61, 7.3.2, and 7.4-rc1; mitigation requires kernel upgrade and reboot, or temporary network-level blocking of TCP/2049.

telegram · zaihuapd · Nov 27, 12:57

**「Background」** The Linux kernel&\#x27;s NFS server \(nfsd\) implements the Network File System protocol for serving remote file access; NFSv4.1 and NFSv4.2, introduced in kernel 3.10 \(2013\) and refined in subsequent versions, added stateful operations requiring complex session management via the SEQUENCE operation. The vulnerability arises from unsafe buffer handling in nfsd4\_sequence\(\), a function responsible for preflighting NFSv4.1/4.2 session replies before slot allocation — a design element present since kernel 3.16 \(2014\), as confirmed by the Debian Security Tracker.

**「Impact」** Organizations running exposed NFSv4.1/4.2 servers — including enterprise file servers, NAS devices, and HPC cluster storage nodes — face immediate risk of unauthenticated remote root compromise, requiring urgent patching or firewall-based port restriction.

### [Deterministic Subexponential Algorithm for Discrete Logarithm Problem](https://eprint.iacr.org/2026/3020.pdf) ⭐️ 8.0/10

A new deterministic subexponential-time algorithm for the discrete logarithm problem \(DLP\) over prime fields has been published, achieving runtime 2^O\(b/\(log log b\)\) where b is the bit-length of the modulus. This is the first known deterministic algorithm with subexponential asymptotic complexity for DLP, improving upon decades-old randomized algorithms like Adleman’s 1979 method. The result applies to prime-field DLP—not elliptic curve DLP—and does not break any deployed cryptographic system; it remains asymptotically slower than brute-force methods for all practically used key sizes. No implementation, benchmarking, or extension to elliptic curves is claimed in the paper.

hackernews · yuvadam · Nov 27, 12:08 · [Discussion](https://news.ycombinator.com/item?id=50665968)

**「Background」** The discrete logarithm problem over prime fields has long had randomized subexponential algorithms—most notably Leonard Adleman’s 1979 algorithm—but no deterministic variant with comparable asymptotic performance was known prior to this work. Subexponential time means better than exponential \(e.g., 2^b\) but worse than polynomial \(e.g., b^c\); it sits between those classes and matters for theoretical hardness assumptions underpinning public-key cryptography.

**「Impact」** Cryptographic practitioners face no immediate need to change key sizes or protocols, as the algorithm’s asymptotic advantage only manifests for key lengths far beyond current standards \(e.g., millions of bits\), and it does not apply to elliptic curve groups used in modern systems like TLS or SSH.

**「Community Discussion」** Commenters uniformly agree the result has no practical security impact: \[pcstl\] quantifies that the algorithm only outperforms Baby-Step Giant-Step for &quot;absolutely gigantic keys&quot;, and \[layer8\] notes the existence of a randomized subexponential algorithm since 1979, underscoring that determinism—not subexponentiality—is the novelty. \[cperciva\] observes the expected theoretical parallelism with integer factorization algorithms.

It cites existing verification-focused languages and tools \(SPARK, Dafny, Frama-C, Why3, Verus, TLA+\) and emphasizes practical motivations: sandboxing AI-generated code via WebAssembly, eliminating runtime errors, and making verification accessible to broader developer audiences. The post does not announce a new language or implementation but frames formal verifiability as a core systems-level requirement for future mainstream adoption, especially in safety-critical and AI-augmented contexts.

hackernews · todsacerdoti · Nov 27, 05:22 · [Discussion](https://news.ycombinator.com/item?id=50663089)

**「Formal verification in existing languages」** SPARK is a formally verifiable subset of Ada designed for high-integrity systems, supporting compile-time proofs of absence of runtime errors—including integer overflows—via annotations and automated theorem proving. Tools like Dafny, Frama-C, and Why3 provide similar verification capabilities for C\#, C, and other languages, but they operate as external or add-on frameworks rather than being integrated into the language’s core design and toolchain.

**「Impact」** Developers building safety-critical or AI-integrated systems face increasing pressure to adopt verification practices, yet current tooling requires significant expertise and retrofitting—making verification inaccessible to most mainstream projects; this argument highlights a concrete gap between verified-systems best practices and scalable, developer-friendly language design.

**「Community discussion」** Commenters report real-world use of SPARK for detecting integer overflows in C codebases and describe ongoing work on Zena—a TypeScript-like language targeting WebAssembly GC specifically to sandbox AI-generated code—while others question whether &\#x27;mainstreamness&\#x27; can be designed into a verification-first language or must emerge organically from adoption.

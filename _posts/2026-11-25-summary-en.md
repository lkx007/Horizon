### [Check Point HFS servers compromised via V8 Math.random\(\) PRNG exploit](https://www.greynoise.io/blog/check-point-security-management-servers-intrusion-campaign) ⭐️ 9.0/10

A cyberattack campaign exploited predictable output from JavaScript&\#x27;s Math.random\(\) in Check Point Security Management Server&\#x27;s HFS login cookies to reconstruct the V8 PRNG internal state, recover the session-cookie signing key, and forge authenticated admin sessions—compromising servers across 22 organizations. The attack targeted the /loginSrp1 endpoint, where each POST response included a &\#x27;sid&\#x27; value generated by Math.random\(\), enabling state reconstruction after multiple sequential logins. Attackers subsequently used nftables to patch CVE-2026-98432 on compromised hosts as a defense-in-depth measure against competing actors. The CVE date \(2026\) appears fictional, and no official vendor patch or advisory is cited in the source.

hackernews · louiereederson · Nov 24, 16:32 · [Discussion](https://news.ycombinator.com/item?id=50630594)

**「Background」** Check Point Security Management Server is the central administrative console for configuring and monitoring Check Point firewalls, granting full control over policies, logs, and gateway settings across an organization. The compromised component, HFS \(HTTP File Server\), is part of Check Point’s web-based login infrastructure and uses JavaScript&\#x27;s Math.random\(\)—a non-cryptographic PRNG—to generate session identifiers in login cookies.

**「Impact」** Organizations running unpatched Check Point Security Management Servers are at risk of unauthorized administrative access due to forged session cookies, requiring immediate mitigation such as disabling HFS login or applying vendor-recommended workarounds; GreyNoise confirmed the campaign affected at least 22 organizations across energy, engineering, financial services, government, and manufacturing sectors between October 17 and November 2, 2026.

**「Community discussion」** \[PyWoody\] confirmed the technical chain: sequential login requests yielded enough Math.random\(\) outputs to reconstruct the V8 PRNG state and derive the signing key; \[sigmar\] reported that GT13 actors later deployed nftables rules on compromised systems to mitigate CVE-2026-98432 exploitation by others—though the CVE itself lacks external verification and appears anachronistic.

### [Anthropic Claims Internal Claude Model Proved VP ≠ VNP with Lean 4 Formalization](https://github.com/anthropics/formal-math/blob/main/vp-vnp/README.md) ⭐️ 9.0/10

Anthropic announced on November 24, 2026, a paper titled &\#x27;VP ≠ VNP over every field&\#x27; and a corresponding Lean 4 formalization in the repository anthropics/formal-math, claiming an internal research version of Claude discovered and authored both. The proof purports to establish a superpolynomial arithmetic circuit lower bound for the Hamiltonian cycle polynomial, thereby showing VP is a proper subclass of VNP over all fields—resolving Valiant’s 1979 conjecture—but only within the arithmetic circuit model, not the Boolean Turing machine model \(i.e., it does not address P vs NP\). The Lean 4 development passes three standard axiomatic audits and independent nanoda kernel verification with no remaining &\#x27;sorry&\#x27; placeholders except in reserved files; however, no human mathematician has fully reviewed it, and Appendix Q documents mismatches between the formalized statement and the claimed theorem.

telegram · zaihuapd · Nov 24, 06:02

**「Background」** VP and VNP are algebraic complexity classes introduced by Leslie Valiant in 1979 to study the inherent difficulty of computing polynomial families via arithmetic circuits; VP consists of polynomial families efficiently computable by polynomial-size arithmetic circuits, while VNP contains those whose coefficients are efficiently enumerable—akin to the P vs. NP distinction but for algebraic computation. The conjecture VP ≠ VNP remains one of the central open problems in algebraic complexity theory, with no unconditional lower bound separating them over arbitrary fields prior to this claim.

**「Impact」** If verified, the claimed proof would establish the first unconditional separation between VP and VNP—resolving a foundational 47-year-old conjecture in algebraic complexity theory—but its current status as an unreviewed, AI-authored formalization means no researcher or system can yet rely on it for theoretical derivations or complexity class inferences.

### [GLM-5.4 introduces looped transformer architecture for iterative reasoning](https://simonwillison.net/2026/Nov/23/glm-54/) ⭐️ 8.0/10

Z.ai released GLM-5.4, its first model using a looped transformer architecture in which weight-shared layers execute multiple iterations per forward pass to refine hidden states—enabling deeper computation without increasing parameter count. The model is available exclusively via Z.ai’s paid Coding Plan subscription API \(at https://api.z.ai/api/v1\), not the standard API or open weights; open-sourcing is planned only after safety hardening. It is distinct from prior GLM versions \(e.g., 5.1–5.3\) and coincides with independent adoption of the same architectural idea by Thinking Machines Lab’s Inkling 2 Mini, announced November 20, 2026.

rss · Simon Willison · Nov 23, 23:40

**「Looped transformer architecture」** A looped transformer reuses the same set of transformer layers multiple times per forward pass—iteratively refining hidden states—rather than stacking distinct layers, enabling deeper computation without increasing parameter count. This architectural pattern was independently introduced in late November 2026 by both Z.ai’s GLM-5.4 and Thinking Machines Lab’s Inkling 2 Mini, with the latter specifying three iterations over middle layers for improved reasoning on agentic coding tasks.

**「Consequence for users」** Developers must subscribe to Z.ai’s Coding Plan to access GLM-5.4, and existing OpenAI-compatible tooling \(e.g., llm-zai\) requires updates to support it—prompting temporary community plugin development like Simon Willison’s llm-glm.

### [vLLM-GR: Beam-Search–Optimized Inference for Generative Recommendation](https://vllm.ai/blog/2026-11-24-vllm-gr-announcement) ⭐️ 8.0/10

**「Background」** Generative recommendation models like OneRec must convert long user interaction histories into ranked candidate item IDs—often semantic IDs \(SIDs\)—within strict latency budgets. Standard LLM inference engines lack native support for beam search over constrained vocabularies \(e.g., item catalogs\), shared KV caching across candidate paths, or tight accelerator-host orchestration needed for low-latency, wide-candidate exploration.

**「Solution」** vLLM-GR extends vLLM with a beam-search–enabled execution engine that integrates catalog-aware decoding, shared prompt KV caching, and a prefill–decode–decode \(PDD\) pipeline where the host prepares the next decode step while the accelerator runs the current one. Each beam session tracks branching paths via parent indices, enabling efficient KV state reuse across candidates; catalog filtering prunes invalid SIDs \(e.g., prefixes with no matching items\) directly on the accelerator. Benchmarks show vLLM-GR achieves the lowest P99 latency among comparators—including NVIDIA SID-GR and SGLang Beam—at beam width 256 and batch sizes 4–8 across six accelerators \(RTX PRO 6000, A100, H20, L20, A2, A5\), e.g., 369.4 ms vs. 1,280.1 ms \(SGLang\) on H20 at B=8. Its advantage scales with batch size but not uniformly with beam width: at B=1, NVIDIA SID-GR slightly outperforms it on RTX PRO 6000 \(28.25 ms vs. 29.21 ms\). Memory constraints limit beam-width sweeps on smaller NPUs like A2, yet vLLM-GR completes full sweeps up to 1,024 beams at 8K tokens.

**「Takeaway」** vLLM-GR demonstrates that adapting LLM inference infrastructure—not just models—for generative recommendation yields substantial, hardware-agnostic latency reductions, especially under realistic serving conditions \(wide beams, large batches, catalog constraints\), by unifying beam search semantics with system-level optimizations like shared KV caching and pipelined accelerator-host execution.
